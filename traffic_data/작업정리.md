# 교통 네트워크 데이터 작업 정리

## 1. 프로젝트 목표

서울시 도로망을 그래프 형태로 만들고, 시간대별 속도·지형·강수 데이터를 붙여 경로 탐색 또는 예측 모델에 활용하는 것이 목표이다.

전체 활용 흐름:

```text
ITS 표준 노드/링크
↓
서울시 도로망 그래프 구축
↓
T-data 속도 데이터 LINK_ID 기준 결합
↓
DEM 고도 데이터로 링크별 경사도 추가
↓
레이더강수량으로 시간·공간 기준 강수 피처 추가
↓
Dijkstra 등 경로 탐색 또는 속도/통행시간 예측
```

## 2. 사용할 데이터

| 데이터 | 역할 |
| --- | --- |
| `MOCT_LINK`, `MOCT_NODE` | 도로망 그래프 구축 |
| T-data 1시간 소통정보 | `LINK_ID` 기준으로 시간대별 속도 결합 |
| `DEM.tif` | 링크별 고도·경사도 계산 |
| 레이더강수량 | 시간·공간 기준 강수 피처 생성 |

## 3. ITS 표준 노드/링크 Shapefile 구성

Shapefile은 여러 파일이 한 세트로 있어야 정상적으로 읽힌다.

```text
MOCT_LINK.shp   → 도로 링크의 실제 선형 geometry
MOCT_LINK.dbf   → 링크 속성 테이블
MOCT_LINK.shx   → shp 인덱스
MOCT_LINK.prj   → 좌표계 정보
MOCT_LINK.cpg   → 문자 인코딩 정보

MOCT_NODE.shp   → 노드 geometry
MOCT_NODE.dbf   → 노드 속성 테이블
MOCT_NODE.shx   → shp 인덱스
MOCT_NODE.prj   → 좌표계 정보
MOCT_NODE.cpg   → 문자 인코딩 정보

MULTILINK.dbf   → 복합 링크 관련 속성
TURNINFO.dbf    → 회전 제한/회전 정보
```

`.shp`, `.dbf`, `.shx`, `.prj`, `.cpg`는 한 세트로 같은 폴더에 같이 둬야 한다.

| 데이터 | 역할 |
| --- | --- |
| `MOCT_LINK.shp` | 도로 구간, 즉 그래프의 간선 |
| `MOCT_NODE.shp` | 교차점/연결점, 즉 그래프의 노드 |
| `MOCT_LINK.dbf` | 링크 ID, 도로명, 길이, 시작 노드, 끝 노드 같은 속성 |
| `TURNINFO.dbf` | 좌회전/우회전/유턴 가능 여부 같은 회전 정보 |

| 파일 | 지금 당장 필요 여부 | 이유 |
| --- | --- | --- |
| `MOCT_LINK.shp/dbf/shx/prj/cpg` | 필수 | 도로 링크, 속성, 좌표계 |
| `MOCT_NODE.shp/dbf/shx/prj/cpg` | 선택 | 노드 좌표/교차점 확인용 |
| `MULTILINK.dbf` | 선택 | 복합 링크 처리용 |
| `TURNINFO.dbf` | 선택 | 좌회전/우회전/유턴 제한 분석용 |
| 내역서 | 불필요 | 메타 정보일 가능성이 큼 |

| `geometry` | 도로 선형 좌표 | 지도 시각화, DEM 고도 추출 |

## 6. 좌표계 변환

지도 시각화, T-data, 기상 데이터와 결합할 때는 WGS84 위경도 좌표계가 필요할 수 있다.

GeoPandas에서는 다음처럼 변환한다.

```python
link_wgs = link.to_crs(epsg=4326)
```

주의할 점:

- 원본 `LENGTH`는 원본 투영 좌표계 기준 속성으로 유지하는 것이 좋다.
- 위경도 좌표계에서 직접 길이·면적을 계산하면 값이 왜곡될 수 있다.
- geometry 시각화나 외부 데이터 매칭에는 WGS84가 편하고, 거리·길이 계산에는 미터 단위 투영 좌표계가 적합하다.

## 7. 서울 링크 추출

서울시 기준 분석이므로 먼저 전국 링크 중 서울 근처 링크만 추출했다.

초기 아이디어는 다음처럼 위경도 변환 후 중심점 기준으로 필터링하는 방식이었다.

```python
import geopandas as gpd

link = gpd.read_file("MOCT_LINK.shp")

# 위경도로 변환
link_wgs = link.to_crs(epsg=4326)

# geometry 중심점 계산
link_wgs["centroid"] = link_wgs.geometry.centroid
link_wgs["lon"] = link_wgs["centroid"].x
link_wgs["lat"] = link_wgs["centroid"].y

# 서울 대략 범위로 필터링
seoul_link = link_wgs[
    (link_wgs["lon"] >= 126.75) & (link_wgs["lon"] <= 127.20) &
    (link_wgs["lat"] >= 37.40) & (link_wgs["lat"] <= 37.72)
].copy()

print(seoul_link.shape)
print(seoul_link.head())
```

하지만 현재 작업 파일에서는 중심점 필터 대신 bbox와 링크 geometry가 교차하는지 보는 방식으로 정리했다.

현재 추출 스크립트:

```text
traffic_data/extract_seoul_links.py
```

사용한 서울 대략 bbox:

```text
경도: 126.75 ~ 127.20
위도: 37.40 ~ 37.72
```

현재 작업 방식:

1. 서울 bbox를 `EPSG:4326` 위경도 기준으로 만든다.
2. bbox를 원본 링크 데이터의 좌표계로 변환한다.
3. 원본 링크와 bbox가 교차하는 링크만 남긴다.

서울 추출 결과:

| 항목 | 값 |
| --- | --- |
| 서울 추정 링크 수 | `109,633`개 |
| 산출 Shapefile | `traffic_data/seoul_link.shp` |
| 산출 CSV | `traffic_data/seoul_link_attr.csv` |

주의:

- 현재 방식은 정확한 서울 행정경계 기준이 아니라 bbox 기준이다.
- 서울 바깥의 경기/인천 일부 링크가 섞일 수 있다.
- 진짜 서울 행정구역 안의 링크만 필요하면 서울시 행정경계 Shapefile 또는 GeoJSON을 받아서 `clip`이나 `sjoin`으로 잘라야 한다.

## 12. T-data API 작업 준비

T-data 1시간 링크 소통정보를 가져오기 위한 폴더를 따로 만들었다.

```text
tdata/
```

추가한 파일:

```text
tdata/fetch_tdata_sample.py
tdata/README.md
```

API 키는 코드에 직접 넣지 않고 환경변수 `TDATA_API_KEY`에서 읽도록 했다.

Windows `cmd`에서 실행 예시:

```bat
.venv\Scripts\activate.bat
set TDATA_API_KEY=본인_API_키
cd tdata
python fetch_tdata_sample.py --date 20210101
```

PowerShell에서 실행 예시:

```powershell
$env:TDATA_API_KEY="본인_API_키"
cd tdata
python fetch_tdata_sample.py --date 20210101
```

생성 예정 파일:

```text
tdata/raw/topis_link_speed_20210101.txt
tdata/processed/topis_link_speed_20210101.csv
```

T-data 응답을 받은 뒤 가장 먼저 확인할 것:

- 실제 링크 ID 컬럼명
- 시간 컬럼명
- 평균 속도 컬럼명
- `traffic_data/seoul_link_attr.csv`의 `LINK_ID`와 조인 가능 여부
